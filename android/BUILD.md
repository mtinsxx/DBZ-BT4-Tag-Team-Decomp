# Android LLVM and native runtime bring-up

The Android code is built ahead of time on the development host. Nothing
translates or compiles executable game code on the phone. The original game
sources, PS2 floating-point helpers, GS/VU implementations and legal skeleton
data remain the inputs. No missing-symbol stubs are generated by these tools.

## Toolchain

Use Linux x86_64, matching LLVM/Clang/libclang 23, Python >= 3.11, CMake, Ninja,
NDK r28c, SDL3 3.4.12 built for Android, glslangValidator and SPIR-V Tools.
The wrapper repository's `tools/cloud/env.sh` configures the validated tools.
LLVM 23 emits AArch64 machine objects; the NDK supplies Android headers,
startup objects, libraries and the final linker. Do not feed LLVM 23 IR to
the NDK's older LLVM tools. Target: `aarch64-linux-android28`, `arm64-v8a`.

## Verify the compiler transformation

```bash
cmake -S android -B build/android-host -G Ninja \
  -DBT4_ENABLE_LLVM_TESTS=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build/android-host --parallel 4
ctest --test-dir build/android-host --output-on-failure
```

`llvm_guest_abi` checks compact structure layouts, NULL, bounds, static
initializers, reads/writes, memcpy, mixed integer/pointer callbacks, direct
cross-TU signature mismatches, a variadic declaration of a fixed-argument
function, and an ordinary native callback with a pointer outside the window.
It tests hardware-float/variadic bridges and rejects an unadapted native
floating callback instead of using an incompatible calling convention.
It also compiles the **original** `src/sys/list.c` through `ptr32.py` and the
ELF pass and executes list operations with its actual 32-bit fields. The
test runs in three separate PIE processes, emits Android ARM64 objects, and
checks that the original Mach-O mode still emits an Apple Silicon object.
Host execution is not Android gameplay validation.

The other CTest cases cover the touchscreen bridge, safe address mappings,
integer-register math helpers and ISO9660 metadata lookup. The ISO test builds
its own synthetic image; it contains no commercial files or game data.

## Compile the original game code

```bash
python3 android/tools/build_game.py --build build/android-game --compile-only
```

All 274 C translation units selected by the existing `portsrc.sources()`
are prepared from their original decompilation attempts. `eeconst.py`
preserves the PS2 compiler's constant rules and `ptr32.py` preserves compact
game pointers. The frontend emits unoptimized IR so the window pass runs
before ordinary optimizer transformations. Each module publishes its
function signature kinds before lowering. The pass verifies IR after each
stage; all transformed modules then use LLVM 23's PIC AArch64 code generator.
The result is `libbt4_game_code.a`, per-source logs and `report.json`.
Compilation failures return nonzero and prevent a claimed final link.

For a small, strictly linked set of real engine functions:

```bash
python3 android/tools/build_game.py --build build/android-subset \
  --sources src/sys/align.c src/sys/list.c
```

`libbt4_game_subset.so` is deliberately named as a subset. It has no game
entry point or Android UI and must never be packaged as a playable APK.

## Build runtime dependencies and attempt the complete link

```bash
python3 android/tools/build_dependencies.py --build build/android-dependencies
python3 android/tools/build_runtime.py --game-build build/android-game \
  --build build/android-runtime
```

The dependency build verifies the locked OpenSSL/curl archives and builds
ARM64 PIC static libraries. Their headers are installed alongside Android
SDL3 in `BT4_ANDROID_PREFIX`; host libraries must not be substituted. Native
TLS trust-store selection still requires Android runtime integration.

The runtime builder includes the original platform sources, software-float
maths, VU references, GS/VU1 renderer, audio, menus, network sources and Dear
ImGui. It generates the original SPIR-V/GLSL shader headers, including the
two GS fragment variants; keeps native floating-point compilation separate
from simulation code; assembles the legal blank data tables; and collects
runtime signatures before lowering the game objects again. The final link
uses `--no-undefined`, `-Bsymbolic`, PIC and 16 KiB segment alignment. DirectX
9's Windows-only ImGui backend is excluded, as in the desktop build tool.
The game include directory uses `-iquote`, so its `sys/file.h` cannot shadow
Android's system `<sys/file.h>`.

Each build directory records `report.json` and per-source `.log` files.
The final `link.log` retains every unresolved symbol if linkage fails.
`--reuse-ir` is an explicit developer shortcut, valid only when frontend
sources, headers and flags are unchanged; it always reruns lowering/codegen.
It must not be used to conceal a failed or stale frontend stage.

The current complete link remains blocked by **6 legacy SDK/CRI symbols**
referenced by the original data tables, down from the fixed 102-symbol baseline.
See [SDK_RECONSTRUCTION.md](SDK_RECONSTRUCTION.md) for the 95 real functions
and verified TLB scalar correction. All 274 game and 128 runtime/vendor
translation units compile; the link still fails. See [SDK_BLOCKERS.md](SDK_BLOCKERS.md).
There is no complete engine `.so` or APK to install.

The ISO9660 reader supplies real `sceCdSearchFile` metadata from the user ISO
selected through `BT4_ISO`, including its actual sector and size. It supports
seekable ISO9660 primary-volume files and bounded directory traversal, not
multi-extent files. It does not replace the existing BT4 executable/profile
verification or the still-pending Android importer and storage lifecycle.

## Memory and ABI constraints

- `Port_Window` is configured at constructor priority 101 from the actual
  ELF load bias minus `0x20000000`. ASLR remains enabled.
- Per-module full-width callback signatures register at priority 102.
  Compact static pointer initializers execute at priority 103, after ELF
  relocation. Assembly-table fixups run at priority 104, before the game's
  default-priority memory constructor. Table layouts and numeric entries stay
  unchanged; symbolic `.long` pointers use checked full-width ELF relocations
  followed by compact stores. No `R_AARCH64_ABS32` remains in the attempted link.
- No ELF32 absolute pointer relocations are requested. The source data type
  stays four bytes; startup code writes the window-relative value.
- Encoding a non-null pointer at offset zero or outside `[1, 0xffffffff]`
  fails explicitly. Host allocations passed through ordinary native
  arguments need not be in the window. Pointers stored in compact game
  fields do, including callbacks, locals and file/player handles.
- Callback registration is startup-only, before guest threads run; modules
  cannot be unloaded while guest callbacks can still reference them.
- Both public functions (including those named only in disc tables) and
  address-taken static functions register. A thread-local cache avoids repeated
  full registry scans for callback parameters. Host registration/fixup tables
  live in `.porthst`, outside deterministic game snapshots/checksums.
- Direct software-float/native-float calls use noinline integer-bit thunks,
  including libc variadic doubles. The menu's `__floatundisf` helper returns
  raw float bits in an integer register instead of the NDK's native-FP ABI.
  Native or unknown floating callbacks from guest code still fail explicitly
  until their adapter is supplied; this is a remaining ABI limitation.
- Android keeps ART/debuggerd's signal handlers. The desktop crash handler
  is not installed; `Port_AndroidDiagnostic` logs the runtime stage and guest
  base without claiming to replace Android tombstones.

The remaining runtime work includes data-list addressing for a PIE shared
library, explicit initialization after legally provided data is available,
execution on a guest-window stack, auditing native/software-float ABI
boundaries, Activity/JNI/lifecycle, Vulkan presentation and real-device
testing. A successful object/archive or shared-library build alone does not
establish correctness of those systems. No APK is produced by these tools.
